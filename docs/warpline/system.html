Warpline · the system map & user flows

How the whole thing connects — and how you move through it.

One read-only spine today: git flows up through ABSORB into the WARP, the engine reads meaning, and two surfaces show you what bytes can't say.

This is the UX / system map — distinct from the vision page. Where the architecture diagram answers what is it, this answers where do I stand and what do I press. Everything drawn here is Phase 1: read-only over real git.

01 · The system map

Five layers. Data flows up; nothing flows back.

Git is the floor, not the foundation. Your real branches are absorbed into the WARP — a content-addressed store of meaning — which the engine reads to diff, predict, and run the oracle. Two surfaces sit on top: the CLI and the GUI. In Phase 1 every arrow points up: read-only, by construction.

Layer 1 · the floor git
Real branches, real commits, real merge-tree. Warpline never touches HEAD, the index, or the worktree — it reads refs through a throwaway worktree.
branchAbranchBmerge-basegit merge-tree (the reality check)
↑ ABSORB  ·  absorb(gitRef) → WarpState  ·  lossless lift, drops name/path/position
Layer 2 · the truth the WARP
A content-addressed store of meaning. Each symbol is lifted to a WarpObject whose essence-hash moves iff the meaning moves — so a rename is the empty delta. A WarpState = the whole graph at a ref, keyed by stateId.
WarpObject · kind+contract+edgescontentId = essence:v0:sha256WarpState · stateId
↑ the engine reads the WARP  ·  never the bytes
Layer 3 · the engine diff · predict · oracle
diff(base, branch) → a SemDelta (born / retired / contract-changed / edge-Δ / the empty rename). predict(ΔA, ΔB) → {autoClean, knots, dangling}. oracle(A, B) compares meaning's prediction against git's actual merge and scores the confusion matrix → a verdict.
SemDeltapredict → knots / danglingoracle → CONVERGENT / DIVERGENTJustification (actor · intent · ripple)
↑ appends an OracleRecord → .warpline/oracle.jsonl
Layer 4 · the surfaces CLI & the GUI
The CLI (warpline oracle / absorb) writes the ledger. The GUI — a section in the Platform (paradigm serve) — reads that same ledger, runs compute-only endpoints in-process, and repaints live over a WS bus. No reachable write path.
warpline oracle / absorb (CLI)Oracle Divergence Viewer (GUI)/api/warpline · forecast · diff · ledger

Phase 1 is read-only forever — the GUI's weave verb exits 2; the router can never construct it. Read-only is structural, not policed.

02 · The user flows

Three journeys you can run on this repo today.

Each is a numbered step-flow grounded in the real commands and the real OracleRecord shape. No write path is involved — these are reads, forecasts, and scored comparisons.

01 Review a merge before landing surface: GUI · weave-forecast · ephemeral

STEP 1

Pick two branches

In the ledger rail's RefPicker, choose branchA and branchB from GET /refs. Run stays disabled until they differ.

↳ OracleLedgerRail · RefPicker

STEP 2

Forecast the weave

Press Preview. Posts /forecast {vsGit:true} — fast, ephemeral, no ledger row. The engine predicts from meaning only.

↳ POST /api/warpline/forecast

STEP 3

Inspect knots & dangles

Read prediction.{autoClean, knots, dangling}: how many symbols auto-weave, which symbols knot, any dangling references.

↳ DivergencePanel · KnotRender / DangleRender

STEP 4

Decide

Merge-day becomes a forecast you read first. Land the clean ones; route the knots to a human before they ever hit the worktree.

↳ read-only — you decide, the tool doesn't
A forecast, not a surprise — you see the weave before you commit to it.
02 Catch a divergence — git CLEAN, Warpline DIVERGENT surface: the Oracle · the headline moment

STEP 1

Run the oracle

Two branches touch one .ts file. A renames getUser→fetchUser; B adds a call to getUser(). Run it.

↳ warpline oracle A B  ·  POST /oracle

STEP 2

Two trusted oracles contradict

Left = git: CLEAN ✓ — git merge-tree finds 0 conflicts; it would ship. Right = Warpline: DIVERGENT.

↳ MeaningVsBytesSplit · the seam pulses

STEP 3

The dangling call

The divergeMeaningOnly cell glows: a call into a function that no longer exists. Click it → the real broken symbol.

↳ ConfusionMatrix ★ · DangleRender

⬡ The OracleRecord this writes · the experimental result · .warpline/oracle.jsonl

{
  ts: "2026-06-23T…", branchA: "feat/rename", branchB: "feat/new-call",
  prediction: { autoClean: […], knots: [], dangling: [{ fromSymbol, edgeKind:"uses", danglingTargetSymbol:"getUser", retiredBy:"A" }] },
  gitReality: { conflicted: false, conflictSymbols: [], conflictPaths: [] },
  convergence: { agreeClean:[…], divergeGitOnly:[], divergeMeaningOnly: ["getUser"], score, verdict: "DIVERGENT" },
  justifications: { A:{actor, intent}, B:{actor, intent} }
}
git merged the bytes. Warpline saw the break in the meaning — the one cell allowed to glow.
03 The CLI ↔ GUI handoff — run in the terminal, watch it land in the ledger surface: CLI → ledger → GUI, live

STEP 1

Run the CLI

From a terminal: warpline oracle main feat/x. The engine absorbs both refs, predicts, runs git's real merge, scores.

↳ same engine fns the GUI imports in-process

STEP 2

It appends one row

A single OracleRecord is appended to .warpline/oracle.jsonl — the append-only ledger both surfaces read.

↳ the ledger is the shared substrate

STEP 3

The GUI repaints live

The Platform fs.watches the ledger → fires warpline:oracle-record-appended over the WS bus. The rail prepends the row — no poll, no refresh.

↳ OracleLedgerRail · WS live repaint
The terminal and the screen are two windows onto one ledger — run anywhere, see it everywhere.
