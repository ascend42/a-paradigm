# Migration Prompt: Migrate Existing Codebase to Paradigm

> **Use this prompt to guide an AI agent through migrating an existing codebase to Paradigm's structured format.**

## Overview

You are helping migrate an existing codebase to use **Paradigm**, a structured AI-assisted development framework. This migration will create a `.paradigm/` directory with configuration files, symbol definitions, and team wisdom.

## Phase 1: Discovery

### 1.1 Analyze Project Structure

First, understand the codebase:

```
1. Identify the primary language/framework (package.json, requirements.txt, go.mod, Cargo.toml)
2. Map the directory structure - note patterns like:
   - src/, lib/, app/ → source code
   - components/, features/ → UI/domain code
   - api/, routes/, endpoints/ → API layer
   - auth/, middleware/ → security layer
   - tests/, __tests__/ → testing
3. Find existing documentation (README.md, CONTRIBUTING.md, docs/)
4. Check for existing IDE instructions (.cursorrules, CLAUDE.md, .github/copilot-instructions.md)
```

### 1.2 Identify Symbols

Map existing code concepts to Paradigm symbols:

| Symbol | Type | Look For |
|--------|------|----------|
| `@` | Feature | Main user-facing capabilities, routes, commands |
| `#` | Component | Reusable modules, utilities, services |
| `^` | Gate | Auth middleware, permission checks, guards |
| `!` | Signal | Events emitted, webhooks, notifications |
| `%` | State | Redux stores, context providers, global state |
| `$` | Flow | Multi-step processes, sagas, workflows |
| `&` | Integration | External APIs, third-party services |

### 1.3 Document Authorization

Find and document:
- Authentication methods (JWT, session, OAuth)
- Authorization patterns (RBAC, ABAC, ownership)
- Protected routes/endpoints
- Permission checks in code

## Phase 2: Core File Generation

### 2.1 Create .paradigm/config.yaml

```yaml
version: "1.0"
project: "{PROJECT_NAME}"

agent-guidelines:
  overview: |
    {Brief description of what this project does}
  how-to-use:
    - Check .paradigm/specs/ for patterns and conventions
    - Use symbol prefixes: @feature #component ^gate !signal %state $flow
    - Run `paradigm beacon` for quick context
    - Run `paradigm ripple @symbol` before modifying symbols

symbol-system:
  "@":
    name: Feature
    description: User-facing capabilities
    examples: ["{@example-feature}"]
  "#":
    name: Component
    description: Reusable code modules
    examples: ["#{example-component}"]
  "^":
    name: Gate
    description: Authorization gates
    examples: ["^{example-gate}"]
  "!":
    name: Signal
    description: Events and side effects
    examples: ["!{example-signal}"]
  "%":
    name: State
    description: Application state
    examples: ["%{example-state}"]
  "$":
    name: Flow
    description: Multi-step processes
    examples: ["${example-flow}"]
  "&":
    name: Integration
    description: External services
    examples: ["&{example-integration}"]

logging:
  enforce: true
  default-level: debug

scan:
  enabled: true
  skip:
    - node_modules
    - dist
    - build
    - .git
    - coverage

conventions:
  - Use kebab-case for symbol IDs
  - ALWAYS use Paradigm logger, NEVER raw console.log/print
  - Document flows when logic spans 3+ components
```

### 2.3 Create portal.yaml (if authorization exists)

```yaml
version: "1.0"
description: Security gates and authorization

gates:
  ^authenticated:
    description: User must be logged in
    check: session.userId != null
    failure: Redirect to login

  ^admin-only:
    description: Admin role required
    check: user.role === 'admin'
    failure: 403 Forbidden

  ^{resource}-owner:
    description: User must own the resource
    check: resource.ownerId === user.id
    failure: 403 Forbidden

routes:
  /api/*:
    gates: [^authenticated]

  /admin/*:
    gates: [^authenticated, ^admin-only]

  /api/{resource}/:id:
    gates: [^authenticated, ^{resource}-owner]
    methods: [PUT, PATCH, DELETE]
```

## Phase 3: Purpose File Creation

### 3.1 Root .purpose

Create in project root:

```yaml
# Project Purpose
name: "{PROJECT_NAME}"
version: "1.0"
description: |
  {One paragraph describing what this project does}

features:
  @{feature-1}:
    description: {What it does}
    status: active

  @{feature-2}:
    description: {What it does}
    status: active

# Key integrations
integrations:
  &{integration-1}:
    description: {What it connects to}
    type: {api|database|service}
```

### 3.2 Directory .purpose Files

Create .purpose files in key directories:

**src/features/{feature}/.purpose**
```yaml
feature: @{feature}
description: |
  {What this feature does}

components:
  #{component-1}:
    description: {What it does}
    file: {filename}.ts

signals:
  !{signal-1}:
    description: Emitted when {event}
    payload: {type}

flows:
  ${flow-1}:
    description: {Multi-step process}
    steps:
      1. {Step description}
      2. {Step description}

dependencies:
  - @{other-feature}
  - #{shared-component}
```

**src/auth/.purpose**
```yaml
feature: ^authentication
description: |
  Authentication and authorization layer

gates:
  ^authenticated:
    description: Verifies user session
    implementation: middleware/auth.ts

  ^admin-only:
    description: Requires admin role
    implementation: middleware/admin.ts

signals:
  !login-success:
    description: User successfully authenticated
  !login-failed:
    description: Authentication failed
```

### 4.2 Create .paradigm/wisdom/antipatterns.yaml

Document what NOT to do:

```yaml
version: "1.0"
description: Common mistakes to avoid

antipatterns:
  - id: api-001
    description: Don't call external APIs in render loops
    reason: Performance degradation and rate limiting
    alternative: Use caching or memoization
    symbols: ["#api-client"]

  - id: auth-001
    description: Never store passwords in plain text
    reason: Security vulnerability
    alternative: Use bcrypt hashing
    symbols: ["^authenticated"]
```

## Tips for AI Agents

1. **Start with discovery** - Don't generate files until you understand the codebase
2. **Use existing patterns** - Look at how similar projects are structured
3. **Be incremental** - Create core files first, add detail later
4. **Validate often** - Run `paradigm doctor` after each phase
5. **Ask for clarification** - If unsure about a symbol or gate, ask the user

## Common Patterns by Framework

### Next.js / React
- Features: `app/` routes, `src/features/`
- Components: `components/`, `src/ui/`
- State: React context, Redux stores

### Express / Node.js
- Features: `routes/`, `controllers/`
- Components: `services/`, `lib/`
- Gates: `middleware/auth.js`

### Django / Python
- Features: Apps in project root
- Components: `utils/`, services
- Gates: `decorators.py`, permissions

### Go
- Features: `cmd/`, handlers
- Components: `internal/`, `pkg/`
- Gates: middleware functions
