# FTUX Friction Report — 2026-05-02

**Scenario:** A new user has just installed Paradigm, run `paradigm shift`, connected Claude Code + MCP + the agent team, and is now in their Claude session asking: **"What can paradigm do?"**

**Agent:** Nora (ftux)
**Surfaces read:** README.md, docs/guides/quick-start.md, docs/guides/mcp-setup.md, docs/guides/agents.md, plugins/paradigm/README.md, CHANGELOG.md (latest entry only)
**Simulation integrity:** Source code, .purpose files, internal specs, and .paradigm/** metadata were not read.

---

## 1. What surfaces exist to answer this question

When a new user asks "what can paradigm do?", the surfaces available are:

| Surface | Route to get there | Relevance |
|---|---|---|
| **README.md** | npm page link, GitHub, docs link in plugin README | Primary pitch + concept overview |
| **plugins/paradigm/README.md** | Claude Code plugin marketplace entry | Focused Claude Code capabilities |
| **docs/guides/quick-start.md** | Linked from README "Quick Start Guide" | Setup guide, not a capability answer |
| **docs/guides/mcp-setup.md** | Linked from README "Full MCP tool list" | MCP tools list, deep detail |
| **docs/guides/agents.md** | Linked from README "Guide →" under Ecosystem | Agent system detail |
| **CHANGELOG.md** | Linked from README | Latest feature summary (v6.2.0) |
| **llms.txt** | Linked in README's AI Agents section | Structured for AI, not human new users |

The **primary answer surface** is README.md — it is the entry point for all new users regardless of how they found Paradigm. The plugin README is the second surface for Claude Code users who installed via `/plugin marketplace add`.

---

## 2. What a first-time user actually finds

### Step 1: User reads the README

The user lands on the headline: **"One command to make your codebase AI-ready."**

They see `paradigm shift` prominently featured with a terminal screenshot. The README is well-structured and clearly written. They find:

- A benchmark table (42% faster, 8.5x less tokens, 88% cheaper)
- A "Concepts" section explaining five symbols (`#`, `$`, `^`, `!`, `~`)
- An "Integrations" section for IDE support and MCP
- A "Useful commands" table
- An "Ecosystem" section listing Sentinel, University, Conductor, multi-agent orchestration, Decisions, Workspaces

This is a **good starting point**. However the user is now in their active Claude session — they are not reading a website. They want Claude to tell them what paradigm can do.

### Step 2: User is inside Claude Code and types "what can paradigm do?"

The user has the plugin installed. Claude has access to 50+ MCP tools. But there is **no user-facing guidance in the surfaces read** that explains what Claude should say in response to this natural-language question.

The plugin README lists 50+ tools in a table. The mcp-setup.md lists 5 representative tools. The README says "50+ tools" twice but never names more than ~8 in the main body. The CHANGELOG v6.2.0 entry describes Atlas/arch tools in detail — but only a user who reads every changelog entry would find that.

The user's experience depends entirely on whether Claude can synthesize a coherent "what can I do for you" answer from the tool schemas alone — there is no dedicated capability summary optimized for this question.

## 3. Friction points

### F-01 — No dedicated "what can paradigm do?" answer surface
**Type:** missing_coverage
**Severity:** HIGH

There is no single surface that answers the question "what can paradigm do?" in the context of an active Claude session. The README answers it at the product level (install pitch). The plugin README answers it at the tools-list level. But neither is written as a conversational capability summary that Claude can use as a first-person response when a user asks the question mid-session.

A user asking Claude "what can paradigm do?" will either get a generic paraphrase of the README (if Claude has context) or a tool-schema dump (if Claude doesn't). Neither is the experience the user deserves at this moment.

**What's missing:** A `paradigm://context/capabilities` MCP resource or a `paradigm_capabilities` tool that returns a structured, human-readable summary of what paradigm can do — organized by use case, not by tool name.

---

### F-02 — "50+ tools" claim with no organized discovery path
**Type:** buried_info
**Severity:** MEDIUM

The README mentions "50+ tools" twice but only names 5–8 of them at any point in the main body. The plugin README provides a table organized by category (Core, Navigation, Purpose Management, Portal/Auth, Wisdom, History, Flows, Sentinel, Lore, Orchestration, Governance, Tags, Context, Index), which is much better — but this table is only seen by users who read the plugin README directly, not users who installed via npm.

A new user who installed via `npm install -g @a-company/paradigm` and ran `paradigm mcp setup --client claude-code` manually never encounters the plugin README unless they go to GitHub. They are told to ask Claude "What Paradigm tools do you have access to?" (from both quick-start.md and mcp-setup.md) but this verification step is about confirming MCP is connected, not about understanding capabilities.

**Compounding factor:** The plugin README and mcp-setup.md disagree on tool counts. Plugin README says "50+ MCP tools". The mcp-setup.md "Using Paradigm MCP" section lists only 5 tools in its table (`paradigm_search`, `paradigm_ripple`, `paradigm_related`, `paradigm_status`, `paradigm_gates_for_route`). A user who reads both will be confused about where the other 45+ tools are documented.

---

### F-03 — Two competing setup paths with unclear which is current
**Type:** contradictory
**Severity:** MEDIUM

The quick-start.md guide uses `paradigm init --quick && paradigm sync --all && paradigm mcp setup --client all && paradigm constellation && paradigm beacon && paradigm doctor` as the setup sequence.

The README.md promotes `paradigm shift` as "the one command" and says "That's it."

These are presented as alternatives, but the quick-start guide is titled "Quick Start Guide" and appears to be a step-by-step expansion — yet it uses `paradigm init` not `paradigm shift`. A first-time user who reads the README will believe `paradigm shift` is the current command. A user who then reads the quick-start guide will encounter `paradigm init --quick` and wonder if `shift` superseded `init` or if they are different.

The mcp-setup.md "Next Steps" section says "Run `paradigm shift` to generate `.paradigm/`, `.purpose`, and `portal.yaml`" — which contradicts the quick-start.md's own setup sequence. The user has no way to know which source is current.

---

### F-04 — Agent team capabilities are buried behind the agents.md guide
**Type:** buried_info
**Severity:** MEDIUM

The user ran `paradigm shift` which rostered an agent team. They are now in a Claude session with those agents available. But there is no surface that explains what the team can do together in a session.

The README mentions "The agent team" section with 8 specialist agents and the command `paradigm team orchestrate "..."`. The plugin README lists 5 agents. The agents.md guide is comprehensive but 431 lines long. There is nothing at the "what can I do right now in this session" level.

A first-time user doesn't know that they can say "paradigm team orchestrate 'add authentication to my API'" and have architect + builder + reviewer + tester + security + documentor pipeline the task end-to-end. This is arguably the most valuable thing Paradigm does in a Claude session, and it requires reading Section 2 of agents.md or the README's one-sentence mention to discover it.

---

### F-05 — Enforcement hook behavior described only after setup
**Type:** assumed_context
**Severity:** LOW-MEDIUM

The Stop hook "blocks" sessions if `.purpose` files are not updated. This is critical information for a new user's first session — because their first real task will trigger the hook. The README describes hooks clearly in the "Enforcement hooks" table. The plugin README describes it in "How Enforcement Works."

However, neither surface proactively warns the user about the hook at the moment they are about to do their first edit. The quick-start.md doesn't mention the Stop hook at all. The mcp-setup.md doesn't mention it. A user who read only quick-start.md and mcp-setup.md (following the docs/guides path) will hit the Stop hook as a surprise on their first session end.

The consequence: the user's first experience with the enforcement system is a blocked session, not a guided introduction to it.

---

### F-06 — The "Ecosystem" section lists six systems with no relative importance signal
**Type:** assumed_context
**Severity:** LOW

The README Ecosystem section lists Sentinel, University, Conductor, multi-agent orchestration, Decisions, and Workspaces as "Companion tools." All are linked with brief one-line descriptions. There is no signal about which are core (every user needs these) versus advanced (power-user opt-ins).

A new user reading "Sentinel — symbol-correlated incident tracking and failure-pattern matching. `paradigm sentinel`." has no idea if this is something they should set up now, something for teams only, or something that auto-configures. Same for Conductor ("native macOS overlay for multi-session orchestration") — is this required? Is it separate software? It's listed alongside multi-agent orchestration as if they are peers.

The practical effect: a new user asking "what can paradigm do?" will enumerate these six systems as capabilities, not knowing which ones apply to them right now.

---

### F-07 — No "what changed in this version" summary for new users
**Type:** missing_coverage
**Severity:** LOW

The CHANGELOG v6.2.0 entry is detailed and useful — for existing users upgrading. Atlas the Cartographer, arch.yaml, two new MCP tools, `paradigm arch` CLI. But a new user reading the latest changelog entry to understand "what is Paradigm" will form a highly skewed picture: they'll think arch mapping is a central feature, not a v6.2 addition to an established system.

The CHANGELOG convention (no Unreleased section, every push is a release) is good practice but means there's no "new to Paradigm? Here's what matters" landing point in the changelog surface.

---

## 4. Verdict: Most critical gap

**F-01 is the most critical gap.** A user who is already set up — plugin installed, `paradigm shift` complete, agent team rostered, MCP connected — and asks Claude "what can paradigm do?" receives no purpose-built answer. They get either a paraphrase of the install pitch (not useful at this stage) or a raw tool list (overwhelming and not use-case oriented).

The missing artifact is a **session-context capability summary**: a short, conversational resource that Claude can surface when asked "what can paradigm do?" in an active session. It should be organized by what the user wants to accomplish ("I want to understand my codebase" → `paradigm_search`, `paradigm_ripple`, `paradigm_navigate`; "I want to build a feature safely" → agent team orchestration + enforcement loop; "I want to manage auth" → portal.yaml + gates tools) rather than by tool names.

The existing `paradigm://context/agent-protocol` MCP resource (mentioned in mcp-setup.md) appears to be the closest thing — but it is described as "detailed workflow instructions" not a capability summary, and it is noted only for Claude Desktop users. A `paradigm://context/capabilities` resource, or enriching the existing protocol resource with a "what I can do for you" section, would close F-01.
