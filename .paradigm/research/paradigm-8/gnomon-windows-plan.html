Gnomon on Windows: the plan

22 October 2026 · drafted by Arky (architecture, build, packaging) and Aegis (security parity) · nothing is built yet, and nothing is decided until you choose below.

In one paragraph. The spec designed Windows in from the start, but almost none of the Windows-specific code exists yet. Getting Gnomon buildable on Windows is four milestones (W0–W3, plus the app shell W6). Getting it shippable takes about ten. Your "just click to approve" idea removes the hardest piece (hardware keys with Windows Hello) from the critical path. Aegis recommends keeping Hello for a small set of high-stakes actions. You need a real x64 Windows PC to finish, because a Mac VM can't stand in for the acceptance tests.

1 · Your idea: click to approve, no Hello

Routine cards get approved by clicking them in the app, with no Windows Hello or password prompt. That drops a lot of work: the hardware key setup, the presence prompt window and probe P02.

What it gives up (Aegis)

Without presence, the approval key is a software key that any program running as you can read. Such a program could sign approvals itself, or fake a click on "Approve" (Windows lets a program send clicks to another window). So on Windows an approval proves "some code running as this user said yes", not "the human said yes". On a Mac, Touch ID or a password proves it was you.

What keeps it honest anyway

  • The kernel accepts decisions only from the verified Gnomon app window, never from scripts, the CLI or a browser tab.
  • Sessions run at Windows' low integrity level, which stops them sending clicks into the app.
  • A permanent "presence: off (Windows)" banner, and the custody level shown in status.
  • Voice approvals are off on Windows. Voice is for talking only.

Aegis's recommendation: a hybrid

Click onlyStill asks Windows Hello (PIN is fine)
Tool permissions, ask-user, plan approval. These are the everyday cards, the same class your Mac caches today.Setting up or rotating your root key; signing config and grants; gate-class cards, "always" rules, installs, budget resume, cloud fallback, API tokens; pairing links; voice enrolment.

Why: that's a handful of prompts a week. If even these were click-only, the budget fuse and permits would only be advisory against any program running as you.

4 · What only you can provide

  • A real x64 Windows PC: Windows 11 Pro, TPM 2.0 (firmware TPM is fine), 16 GB RAM. Any recent mini PC, about $500. It also runs Windows Sandbox for the clean-machine test.
  • Azure Trusted Signing for Windows code signing: an Azure subscription, identity validation (US and Canada individuals qualify), Basic tier at about $10/month (check current pricing). Arky's advice is not to buy an EV certificate: since 2024 it no longer gets instant SmartScreen trust. Expect "unrecognized app" warnings at first, until reputation builds. npm installs mostly avoid this.

5 · Decisions for you

6 · Found on the Mac while planning this

Aegis found that the Mac helper doesn't check who's calling it. The planned check, where the helper answers only the signed kernel (decision D68), isn't built yet. Any program running as you can start the helper and trigger a real Touch ID prompt that shows its own text. It can't sign anything without your touch or password, so your keys stay protected, but it can try to trick you into approving. I told you earlier this check existed; it doesn't yet. It's filed as high priority (T-2026-10-22-004) for Aegis to decide before 8.0: build the check, or list it as a known limitation in the release notes.
