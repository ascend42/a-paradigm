Four levels. One exercise each, on your own repo.

This is a path, not a course. Every level ends with something you can see in your own code. Most exercises are a sentence you say to your agent, because that is how Paradigm is used: you ask, the agent does the bookkeeping, and the checks hold it to that.

The times are our estimates. Nobody has timed them yet.

We built a course first. It recorded 0 uses in 30 days. So the path lives here, in the open, and the quizzes are optional. recorded 2026-09-26, not re-run · decision TD-2026-09-26-846 (teaching-audit.md:93)

The path

  1. See itabout 10 minutes (estimate)You get an impact answer on your own code, from the first prompt.

    After this, you have asked “what does this change touch?” about a module you know, and judged the answer yourself.

    The exercise

    Install, set up a real project of yours, and add the plugin in Claude Code:

    npm install -g @a-company/paradigm
    paradigm shiftin your project
    /plugin marketplace add ascend42/a-paradigm
    /plugin install paradigm@a-paradigm
    then say to your agent Map this codebase with Paradigm: draft .purpose files for the main directories, then tell me what would be affected if I changed a module you know.

    You should see

    An answer that names files and components you recognise. This is the same question asked of Paradigm's own repo, from the command line:

    If the answer on your code is wrong or empty, that is worth knowing after ten minutes and not after a week. Run paradigm doctor and read what it says.

    The practice that belongs here: P1

    Do
    Have the agent map the code before you ask it to change the code.
    Instead of
    Asking for a change and letting the agent find its own way through the files.
    Why
    The agent can only ask the map what a change touches once the map exists.

    Good to know before you start: run paradigm shift on a branch. It writes new files and regenerates instruction files such as CLAUDE.md. Read the diff before you commit.

    Full guide: docs/guides/quick-start.md

  2. G

    Gnomon trackabout 5 minutes (estimate), then ongoingYou approve your first card on the stack.

    After this, your sessions ask in one place and your answers are signed.

    Before you start

    All four must hold, or Gnomon refuses:

    1. An Apple silicon Mac with macOS 15 or later and System Integrity Protection on
    2. Claude Code from the native installer, signed in with your Claude subscription
    3. Touch ID or your login password
    4. Node 24 or later

    The exercise

    gnomonin a repo

    The first run sets up your Mac and asks for Touch ID or your password 2 times. Start a session and ask it to do something that needs permission.

    You should see

    A card on the decision stack. Approve it with Touch ID or your password.

    Practice for this track

    Do
    Read each card before you approve it.
    Instead of
    Making “Always allow” rules early to quiet the stack.
    Why
    Gnomon shows spending and does not cap it, so the cards are the control you have.

    Full guide: the Gnomon page; packages/gnomon/README.md · real · README.md:62-67 · run 2026-11-23

  3. W

    Warpline trackabout 3 minutes (estimate), then ongoingYou run a merge forecast on two of your own branches.

    After this, you have seen what Warpline says about a real merge of yours, and you know it is experimental.

    The exercise

    In a TypeScript repo with two branches:

    npm i -g @a-company/warpline
    warpline oracle <branchA> <branchB>

    You should see

    A prediction, git's real result, and a verdict on whether they agree. On two branches of this repo:

    Practice for this track

    Do
    Treat a flag as a reason to look.
    Instead of
    Treating it as a verdict.
    Why
    In our study, 3 of 18 flags were real defects and 15 were harmless.
    Evidence
    recorded 2026-07-02, not re-run · .paradigm/research/warpline-guard-base-rate/ground-truth.md:13-27

    Full guide: the Warpline page; docs/guides/warpline-project-setup.md

  4. Work with itday oneYou ship one small change with its .purpose kept current and a Symbols: trailer.

    After this, you can read a .purpose file and a portal.yaml, and you know what the agent maintains for you and what is not enforced yet.

    The exercise

    Pick a small, real change.

    say to your agent Make this change: your change. Update the .purpose file for the code you touch in the same change. Then show me the .purpose diff and commit with a Symbols: trailer.

    Read the .purpose diff yourself. It is short. That is the point of this level: you learn the five kinds of symbol by reading them, not by memorising them.

    You should see

    A commit whose subject names its main symbol and whose last line lists every symbol it touched. A real one from this repo:

    If the map looks out of date afterwards, rebuild the index: paradigm reindex. That command is not in 8.1.3 yet; until it ships, ask your agent to reindex.

    The practice that belongs here: P2

    Do
    Let the agent update .purpose in the same change as the code.
    Instead of
    A tidy-up pass afterwards.
    Why
    Once you turn the checks on at balanced, a .purpose file left behind is what blocks the session.

    What is not enforced yet: nothing is. At this level every check is still off. You are relying on the agent following its instructions. Level 2 changes that.

    Full guide: docs/guides/quick-start.md

  5. Trust itweek oneYou choose an enforcement level, trigger a block on purpose, and clear it.

    After this, the checks are on because you turned them on, and you have seen one stop a session.

    The exercise

    Turn the checks on, and look at what you chose:

    paradigm enforcement set balanced
    paradigm enforcement status

    Then trigger a block on purpose.

    say to your agent Change one source file in a directory with a .purpose file, and do not update the .purpose file. Then stop.

    You should see

    The session refuses to stop, and says which description was left behind. Now say “update the .purpose file”, and it stops cleanly. We have not captured a real block message for this page, so there is no excerpt here yet.

    paradigm enforcement status prints a table of checks. At balanced, purpose-coverage is set to block and most others warn.

    The practice that belongs here: P4

    Do
    Turn enforcement on deliberately, and pick the level.
    Instead of
    Assuming the hooks are already checking.
    Why
    The default level is none.

    Also at this level: P3 (ask what a change affects), P5 (gates before endpoints), P6 (decisions and lore as you go), P7 (the team for larger work).

    Full guides: docs/guides/v6-migration.md, section 11 explains the default · docs/guides/decisions.md, sections 1 to 5

  6. Compound itmonth oneYou teach one agent one rule, gate it, and see it applied.

    After this, one thing you know about your codebase is written where an agent will read it next time, and you signed it off.

    Read this first. This is the least proven level. The rules for gated learning are built. We have no evidence yet that what agents learn improves their work: on our own repo the loop reads “FLATLINE: 0 journals / 20 completions”. The class skill is still marked as a draft. Treat this level as a way to write down rules you already trust, with a gate in front of them.

    The exercise

    Pick one rule you keep repeating to your agent. In Claude Code, give it the rule and the agent it is for. Then hold a class term, where the rule is tested before it is kept.

    /paradigm:teachin Claude Code
    /paradigm:class

    You should see

    A notebook entry for that agent, carrying your rule, that you approved. In a later session, the agent applies it without being told.

    The practice that belongs here: P9

    Do
    Treat what an agent learned as provisional until you sign it off.
    Instead of
    Trusting a learning because it was recorded.
    Why
    Since 8.1.1 a learning counts as survived only after two confirmed scenario runs, by a different agent.

    Also at this level: P8 (a small roster), P10 (protocols), P11 (regenerate, don't hand-edit), P12 (typed stores), P13 (doctor after upgrades).

    Full guides: docs/guides/agents.md · docs/guides/learning-scopes.md · real · paradigm doctor; pages/captures/paradigm-doctor.txt · run 2026-11-23

Thirteen practices, each with its reason.

Do, instead of, and why. Where the reason is measured, the measurement is named. Where it is our guidance and nothing more, we say that.

See itthe first prompt

  1. Map first.

    Do
    Have the agent map the code before you ask it to change the code.
    Instead of
    Asking for a change and letting the agent read its way in.
    Why
    Impact questions only work on mapped code. On our repo, paradigm ripple '#init-handler' names its 2 dependents at once.
    Evidence
    pages/captures/paradigm-ripple.txt. Not measured: any saving in tokens or time. Our one study found fewer file reads and more tool calls with Paradigm.

Work with itday one

  1. Keep .purpose current in the same change.

    Do
    Have the agent update .purpose with the code.
    Instead of
    A catch-up pass later.
    Why
    At balanced, purpose-coverage is the check that blocks.
    Evidence
    real · paradigm enforcement status on this repo; pages/captures/counts.txt · run 2026-11-23

Trust itweek one

  1. Ask what it affects before a change that is not trivial.

    Do
    Say “what does this affect?” before the change.
    Instead of
    Finding out from a failing test.
    Why
    The instructions Paradigm generates for your agent ask for it before each task, and there is a skill for it, /paradigm:ripple.
    Evidence
    packages/paradigm/src/core/ide-adapters/claude.ts:110. A caution we owe you: until 7.15.0, ripple could report 0 dependents and "safe to proceed" for a gate in use. Update before you rely on it.

  2. Turn enforcement on deliberately.

    Do
    Choose a level with paradigm enforcement set.
    Instead of
    Assuming the Stop hook already blocks.
    Why
    The default is none. Our own migration guide calls that default the “largest silent behavioral change in v6.x”.
    Evidence
    packages/paradigm/src/core/enforcement/loader.ts:21; docs/guides/v6-migration.md:337-341

  3. Declare gates in portal.yaml before adding an endpoint.

    Do
    Write the gate, then the route.
    Instead of
    Adding auth checks in code and documenting them afterwards.
    Why
    The gate file is the record of who may do what. A portal.yaml that cannot be parsed now fails closed; before that fix, our migration guide calls it “a documented auth-bypass”.
    Evidence
    docs/guides/v6-migration.md:113-120. A limit we owe you: the tool that looks up the gates for a route returns an empty list today, so have the agent read portal.yaml itself.

  4. Record the why as a decision and what happened as lore, as you go.

    Do
    Ask the agent to record a decision when a choice is made, and lore when the work is done.
    Instead of
    Reconstructing it at the end of the week.
    Why
    The next session reads these. This repo holds 138 decisions and 710 lore entries.
    Evidence
    docs/guides/decisions.md, section 3; the lore-required check. Counts: real · ls .paradigm/decisions | wc -l; pages/captures/counts.txt · run 2026-11-23

  5. Use the team for work across three or more files, and say so when you go solo.

    Do
    Let the agent plan larger work with the team, or declare a solo session with paradigm solo <reason>.
    Instead of
    Skipping the team without a record.
    Why
    There is a check for it, orchestration-required, with a threshold of three files.
    Evidence
    paradigm enforcement status on this repo (“Orchestration threshold: 3 files”).

Compound itmonth one

  1. Keep the roster small: three or four agents for a task.

    Do
    Bench the agents you do not need, with paradigm agent bench <id>.
    Instead of
    Keeping all 68 bundled profiles active.
    Why
    Our guidance is that past five the cost outweighs the value.
    Evidence
    docs/guides/agents.md:79. This is guidance from our own use. It has not been measured.

  2. Treat what agents learn as provisional until you sign it off.

    Do
    Review learnings in a class term.
    Instead of
    Trusting the automatic loop alone.
    Why
    On our own repo the loop reads “FLATLINE: 0 journals / 20 completions”. It cannot be relied on by itself.
    Evidence
    real · paradigm doctor; pages/captures/paradigm-doctor.txt · run 2026-11-23

  3. Check for a protocol before repeating a pattern, and record one after.

    Do
    Ask “is there a protocol for this?” first. There is a skill, /paradigm:protocol.
    Instead of
    Solving the same pattern a second way.
    Why
    It is step zero in the instructions Paradigm generates for your agent. This repo has 41 recorded.
    Evidence
    packages/paradigm/src/core/ide-adapters/claude.ts:118; real · ls .paradigm/protocols | wc -l; pages/captures/counts.txt · run 2026-11-23

  4. Regenerate instruction files with paradigm sync. Do not hand-edit them.

    Do
    Change the source, then run paradigm sync.
    Instead of
    Editing the generated CLAUDE.md directly.
    Why
    The next sync rewrites the file, and your edit is gone.
    Evidence
    packages/paradigm/src/core/ide-adapters/index.ts:308-322

  5. Put durable facts in the typed store, not in the agent's native memory.

    Do
    What happened goes to lore, a rule to habits, a reason to a decision.
    Instead of
    Letting everything pile up in one memory file.
    Why
    Typed records can be found and checked. paradigm memory review flags what has piled up.
    Evidence
    packages/paradigm/src/core/ide-adapters/claude.ts:157-169

  6. Run paradigm doctor after every upgrade.

    Do
    Upgrade, then paradigm doctor.
    Instead of
    Assuming an upgrade migrated everything.
    Why
    On our own repo, doctor found 15 dead path references and a list of tool names in permission files that no longer match a tool.
    Evidence
    real · paradigm doctor; pages/captures/paradigm-doctor.txt · run 2026-11-23

The thirteen, as pairs

  1. Map first, then change.
  2. .purpose in the same change.
  3. Ask what it affects, before the change.
  4. Turn enforcement on. It starts off.
  5. Gate first, then the endpoint.
  6. Decision for the why, lore for what happened.
  7. Team for three files or more. Say so when solo.
  8. Three or four agents, not all of them.
  9. A learning is provisional until you sign it.
  10. Look for a protocol first. Record one after.
  11. paradigm sync. Do not hand-edit generated files.
  12. Typed stores, not one memory file.
  13. paradigm doctor after every upgrade.
