## E. Bash `|| true` Regression Test Walkthrough

**Test at `portal-compliance.test.ts:233-286`. Walked through:**

**Sub-test 1 (static assertion, l.237-260):**
```
const src = fs.readFileSync(scriptPath, 'utf-8');  // packages/paradigm/src/commands/hooks/scripts/paradigm-common.sh
const complianceLines = src.split('\n').filter(l => l.includes('paradigm compliance-check'));
expect(complianceLines.length).toBeGreaterThan(0);  // make sure we found lines
for (const line of complianceLines) {
  expect(line).not.toMatch(/\|\|\s*true\s*$/);  // CRITICAL
}
expect(src).toContain('COMPLIANCE_EXIT');
expect(src).toContain('compliance-check failed to run');
```

**Would this fail if someone re-added `|| true`?** YES. I verified by reading the current file — it has lines like `COMPLIANCE_RESULT=$(paradigm compliance-check --json ... 2>/dev/null)` (no `|| true`). If a future dev appended `|| true` to those lines, the regex `/\|\|\s*true\s*$/` on a line containing `paradigm compliance-check` would match → assertion fails → test fails → CI/precommit catches the regression.

**Edge case:** if someone writes `|| true ;` or `|| true  # comment` on the same line, the `\s*$` anchor wouldn't match. This is a mild robustness concern but acceptable for a regression guard — the exact idiom security called out is `|| true\n` (end-of-line).

**Sub-test 2 (shell behavioral, l.262-285):** verifies at the OS/bash level that the old idiom swallows exit codes and the new one doesn't. This is belt-and-suspenders — even if the static assertion had a gap, the behavioral test would catch a live regression.

**Verdict:** the regression test would catch the common reintroduction patterns. Combined with the shell behavioral test, this is sufficient defense.

## Findings

### Finding 1 — `commands/portal-check.ts` (separate file from `portal/check.ts`) does not filter sentinel

- **Category:** improvement
- **Severity:** LOW (cosmetic, not security)
- **Location:** `packages/paradigm/src/commands/portal-check.ts:24-28`
- **Detail:** Wired into the main CLI via `src/index.ts:177`. Its `--json` output includes `usedButUndeclared: report.usedButUndeclared` verbatim — so on a broken portal.yaml, users running `paradigm portal check --json` see `{"usedButUndeclared": ["__portal_unparseable__"], "usedButUndeclaredCount": 1}` without any redacted-classifier context. Non-JSON output relies on `formatComplianceReport` (from `portal-compliance.ts`) which also renders the sentinel as a row in the "Undeclared Gates" section (`:588-599`).
- **Why low:** the sentinel is not a secret; fail-closed behavior is preserved (count > 0). Only affects the developer running the CLI directly, not the stop-hook path, not telemetry, not LLM context (since the string is fixed and carries no file content).
- **Fix:** either (a) filter the sentinel in `formatComplianceReport` (one-line change) and pass through `portalError` metadata to JSON, or (b) land it in v5.38.0 alongside the other CLI polish. Recommend (a) — 5-minute fix — to avoid the "why is `__portal_unparseable__` in my report?" confusion.
- **Blocking ship?** No.

### Finding 2 — `paradigm doctor` redacted-pointer is a partial UX dead-end

- **Category:** improvement
- **Severity:** MEDIUM
- **Location:** `packages/paradigm/src/commands/doctor/index.ts:401-431`
- **Detail:** All redacted error messages (CLI + stop hook + JSON envelope) say: `"portal.yaml unparseable: <errorClass> — run 'paradigm doctor' for details"`. BUT `paradigm doctor` currently reports only `"Invalid YAML: <err.message>"` (l.427) — which DOES include the js-yaml message text (with line number and reason) but does NOT specifically call out duplicate keys with a "which duplicate key? which line?" summary. The user is told to go look at doctor and finds... nothing much more actionable than what their editor's YAML linter would show.
- **Why this matters:** Per spec §5: `paradigm doctor` is supposed to provide the "line-specific info locally where the file is already on disk." It currently doesn't. The spec text ("can be deferred to v5.38.0") says `paradigm doctor` bespoke portal check is deferred — so strictly this is acceptable, but the redacted-pointer UX creates a dead-end that reduces trust in the redaction message itself.

  - (b) Minimal polish: change redacted message to "run 'paradigm portal check' to see the YAML error" (which already prints error.message via `console.error` at `portal/check.ts:120`).
  - (c) Best: implement the bespoke portal check in v5.38.0 per the spec's own §ARCHITECTURAL item list.
- **Blocking ship?** No — spec explicitly defers. But flag for v5.38.0 planning.

### Finding 4 — Duplicated `classifyYamlError` across packages carries drift risk

- **Category:** note
- **Severity:** LOW
- **Location:** `packages/paradigm-mcp/src/utils/yaml-validator.ts:37-60` vs `packages/paradigm/src/core/portal-compliance.ts:115-137`
- **Detail:** Builder explicitly chose to duplicate rather than cross-import. The two implementations match today. Drift risk: if a new YAMLException reason class is added (e.g. for a js-yaml major version bump), the MCP side and CLI side could classify the same exception differently. Observable symptom: stop-hook says `duplicate-key` while `paradigm portal check` says `other` on the same file.
