# Security Audit — v6.0 Breaking Removals

**Date:** 2026-04-22
**Agent:** Security
**Scope:** Four removals planned for v6.0 (per `CHANGELOG.md:54`): `loadPortalConfigLegacy`, `LoreType.decision`, legacy `@a-company/university/src/content/{courses,plsat}/*.json`, server-route dual-layout fallbacks
**Mode:** Read-only

## 1. `loadPortalConfigLegacy` removal — SAFE (with one doc fix)

**Current shape.** `packages/paradigm/src/core/portal-compliance.ts:169-172`:

```ts
export function loadPortalConfigLegacy(rootDir: string): PortalConfig | null {
  const result = loadPortalConfig(rootDir);
  return result.status === 'ok' ? result.data : null;
}
```

Marked `@deprecated since v5.37.12` at `:167`. The shim preserves v5.37.11's null-on-failure return shape for external callers that didn't migrate to the discriminated union in v5.37.12 / 5.38.0 / 5.39.0.

### Finding 1.1: In-monorepo callers — zero use of the shim.

Grep for `loadPortalConfigLegacy` across all of `packages/**` returns exactly two files: the definition (`portal-compliance.ts:169`) and its tests (`packages/paradigm/tests/portal-compliance.test.ts:33,87,89,97,105`). Every in-tree caller (`pm-compliance.ts:172,239`, `flow-validator.ts:333`, `commands/portal/check.ts:31,130`) already uses the discriminated-union `loadPortalConfig`. Removing the shim does not break any first-party code path.

### Finding 1.2: External callers — NOT reachable via the npm package surface.

`packages/paradigm/package.json:6-7` declares only `main: ./dist/index.js` and `types: ./dist/index.d.ts`. `src/index.ts` has **zero `export` statements** (verified by grep `^export ` with no matches) — it is a CLI entry file with a `#!/usr/bin/env node` banner (`tsup.config.ts:9`). `package.json` has no `exports` map and no subpath entry for `portal-compliance`. External npm consumers of `@a-company/paradigm` **cannot `import { loadPortalConfigLegacy } from '@a-company/paradigm'`** — there is no resolvable specifier. Their upgrade from v5.37.11 → v6.0 cannot fail with "loadPortalConfigLegacy undefined at runtime" because the symbol was never a public API to begin with.

The only conceivable path is a consumer reaching into `node_modules/@a-company/paradigm/dist/chunk-*.js` directly — not a supported surface, not a plausible attack surface. tsup tree-shakes so there is no guarantee the symbol even exists in dist under a stable name.

### Finding 1.3: TypeScript import-break is loud.

If anyone did find and import a deep path, TypeScript surfaces the missing export as a compile error (`TS2305`). The concern in the prompt — "a runtime-only caller (dynamic import, mocking path) might not" — applies only to dynamic `await import('@a-company/paradigm/dist/...')`. Such a caller would receive `undefined` and fail on first call, not silently fall through to `null`. There is no "silent fail-open" shape here: the function call would throw `TypeError: loadPortalConfigLegacy is not a function`, which is LOUD and surfaces immediately.

### Finding 1.4: Recommendation.

**Do NOT ship a `loadPortalConfigLegacy` stub that throws in v6.0.** Shipping a named stub implies a public API contract we never had and preserves an indefinite removal debt. Instead:

1. Delete the function from `portal-compliance.ts`.
2. Delete the three `loadPortalConfigLegacy` describe blocks from `tests/portal-compliance.test.ts:87-109`.
3. Keep the doc note at `docs/guides/university.md:327-329` (already accurate). Optionally add a short v6.0 CHANGELOG entry under "Breaking" listing the symbol by name and pointing at the v5.37.12 migration.

### Verdict: SAFE — not a fail-open vector.

## 2. `LoreType.decision` hard error — SAFE; no security-audit-trail path affected

**Current shape.** `packages/paradigm-mcp/src/tools/lore.ts:526-539`:

```ts
// v5.39.0 (D3 locked): soft-deprecate type:'decision' on lore_record.
// Hard error ships v6.0. Still write the entry at v5.39.0 — just warn.
if (type === 'decision') {
  decisionDeprecationNotice = "paradigm_lore_record({type:'decision'}) is deprecated...";
  if (!loreDecisionDeprecationEmitted) { ... log.warn(...) }
}
```

`LoreType` is defined in 5 sibling locations (`packages/paradigm-mcp/src/utils/lore-loader.ts:48`, `packages/paradigm/src/core/lore/types.ts:30`, `packages/paradigm/lore-ui/src/store/loreStore.ts:3`, `packages/paradigm/platform-ui/src/sections/lore/store/loreStore.ts:3`, MCP streams map `packages/paradigm-mcp/src/types/knowledge-streams.ts:207-213`).

### Finding 2.1: No security path writes lore with `type: 'decision'`.

Grep `recordLore` for callers with `type: 'decision'` returns zero matches in library/server code. Every in-tree usage is either (a) a test fixture (`packages/paradigm/src/core/lore/filter.test.ts:37,111`, `packages/paradigm-mcp/tests/decision-migration.test.ts:139,182`), (b) the migration tool itself (`packages/paradigm/src/commands/migrate-decisions.ts:9,294,337,345`) which READS legacy decision entries, or (c) user-facing deprecation strings. Specifically searched:

- No portal-compliance call site writes lore on gate-denied / parse-error outcomes.
- No auth or gate-check path records "decision to deny access" as `type: 'decision'`.
- `checkPortalCompliance` at `portal-compliance.ts:384+` never writes lore; it returns a `ComplianceReport`.
- `paradigm_decision_record` (the canonical replacement) already writes a companion lore entry with `type: 'insight'` and `references.decision_id` (`packages/paradigm-mcp/src/utils/decision-loader.ts:127`), so the narrative audit trail is preserved.

### Finding 2.2: The removal preserves audit trails.

The migration path (`paradigm migrate decisions` at `packages/paradigm/src/commands/migrate-decisions.ts:337`) rewrites existing `type: 'decision'` lore entries to `type: 'insight'` + `references.decision_id`, and writes the structured `TD-*` entry to `.paradigm/decisions/`. Nothing is deleted. A project that skips v5.39.0 → v6.0 directly will hit the hard error on FUTURE `lore_record({type:'decision'})` calls but historical entries remain readable (the reader code at `lore-loader.ts:529` already accepts `decision` as a valid historical enum value and that branch is NOT the code being removed — only the WRITE path rejects).

### Finding 2.3: Risk to confirm before v6.0 ships.

The v6.0 implementation MUST reject the write with a clear error response envelope (structured `err()` pointing at `paradigm_decision_record`), NOT throw an uncaught exception that the MCP tool runner swallows as "no response." An uncaught throw at the tool handler level could silently drop the caller's audit intent if Claude Code's MCP client doesn't surface the error. This is NOT a v5.39.0 bug (today's code writes successfully with a warning) — it's a v6.0 implementation guardrail.

**Recommendation:** v6.0's rejection path must return `err('LORE_DECISION_REMOVED', 'type:decision removed in v6.0; use paradigm_decision_record')` with a clear response envelope, not throw. Verify by checking the v6.0 implementation when it's written: the handler must return an error envelope, and a regression test must assert the JSON response contains the error discriminator.

### Verdict: SAFE — provided v6.0's reject path returns a structured error envelope rather than throwing.

## 3. Legacy PLSAT / courses content removal — SAFE

### Finding 3.1: Server routes already read only the new layout.

`packages/university/src/server/routes/courses.ts:10-12` and `plsat.ts:9-11` (header comments) state: "Old JSON files in content/{courses,plsat}/ are retained on disk (bridge release) but are no longer read here." The body of both files confirms — `courses.ts` reads `content/notes/*.md`, `content/quizzes/*.yaml`, `content/paths/*.yaml` (lines 127-191); `plsat.ts:159,167,192` reads `content/quizzes/Q-plsat-v*.yaml`. There is **no dual-layout fallback in the source** — the "fallback removal" item in the prompt is a misstatement; the routes switched cleanly in v5.39.0, and v6.0 only deletes the orphaned JSON files on disk.

### Finding 3.2: No security contract tied to the legacy JSON content.

Grep `content/courses/.*\.json|content/plsat/.*\.json` across the repo returns 18 hits, all of which are (a) the JSON files themselves, (b) protocols describing how to author quiz content (`.paradigm/protocols/add-plsat-question.protocol`, `add-university-course.protocol`), (c) lore entries describing historical work, or (d) docs. No middleware, redirect, auth, rate-limit, or integrity-check rule references those paths. No test fixture enforces compliance on the old layout. No gate references the path.

### Finding 3.3: PLSAT diploma write path is unaffected.

The security-relevant POST `/api/plsat/diploma` handler (`plsat.ts:220-269`) writes to `.paradigm/university/diplomas/` — independent of content layout. Confirmed unaffected.

### Verdict: SAFE — no security contract attached.

## 5. THE SCENARIO — v5.37.11 → v6.0 skip-upgrade walkthrough

This is the load-bearing question. Walk it carefully.

**Setup.** User pinned `@a-company/paradigm@5.37.11`. Never saw v5.37.12's fail-closed semantics. Upgrades to `@a-company/paradigm@6.0.0`. Their portal.yaml contains a duplicate mapping key (trivially reproduced in real projects over time — Scenario B from the prior audit).

**v5.37.11 behavior (baseline).** `loadPortalConfig` in v5.37.11 was `yaml.load(...)` wrapped in `try { ... } catch { return null }` (see prior audit §2, Scenario B). `checkPortalCompliance` saw `config === null`, entered the "no portal.yaml" branch, and — if scanned files had zero `.purpose` gate references at that moment — returned `status: 'compliant'`. Fail-open.

**v6.0 behavior (subject of audit).** The CLI the user installs is v6.0's shipping build. When they run `paradigm compliance-check` (or the stop hook does), the code path is `portal-compliance.ts:384 → loadPortalConfig → yaml.load throws → classifyYamlError → return { status: 'unparseable', errorClass: 'duplicate-key', detail: 'duplicate mapping key' }`. `checkPortalCompliance` at `:391-418` immediately branches on `status === 'unparseable'` and returns `status: 'violations'` with `usedButUndeclared: ['__portal_unparseable__']`. The stop hook (`paradigm-common.sh`, with the `|| true` mask already removed in v5.37.12) sees `usedButUndeclaredCount > 0` and BLOCKS the session.

**Does the user's OWN TypeScript code still match the `null` shape?** Only if they wrote their own `loadPortalConfig` importing the internal function via a deep path. As §1.2 showed, that path does not exist on the npm package surface. They are consumers of the CLI binary — the CLI calls its own internal API. The shape of the internal API is invisible to them.

**Could the user have imported `loadPortalConfigLegacy` somehow?** Only via `node_modules/@a-company/paradigm/dist/chunk-*.js` (unsupported). Even if they did: v6.0 deletes the symbol, so the import resolves `undefined` and the first call throws `TypeError: loadPortalConfigLegacy is not a function`. LOUD, not silent. This is the OPPOSITE of fail-open.

**Verdict.** The v5.37.11 → v6.0 skip-upgrade PATH FAIL-CLOSES CORRECTLY. The user benefits from v5.37.12's contract even though they never installed it, because the contract lives inside the binary they now run. They will see either a clean pass (portal.yaml parses) or a clean block with "duplicate mapping key detected" (portal.yaml doesn't parse). No scenario produces a `null` gateConfig + silent-compliant response.

## 6. Summary

| Removal | Fail-open risk? | Blocking for v6.0? |
|---|---|---|
| `loadPortalConfigLegacy` delete | No — not a public API surface; internal callers already use discriminated union | No |
| `LoreType.decision` hard-error | No — provided v6.0 returns `err()` envelope not uncaught throw | No (implementation guardrail, not a blocker) |
| Legacy PLSAT / courses JSON delete | No — routes already read new layout only | No |
| Server-route dual-layout fallback | N/A — no fallback exists to remove | No |
| v5.37.11 → v6.0 skip-upgrade | **Fail-closes correctly** — user inherits v5.37.12 contract via new binary | N/A |

**No BLOCKING findings.** v6.0's four removals do not reintroduce any of the five auth-bypass vectors from the v5.37.12 audit. The fail-closed contract (discriminated union + bash `|| true` removal + `Object.keys(Gate[])` fix + error redaction) lives INSIDE the binary and is unaffected by the removal of the back-compat wrapper that merely lost information at the shim boundary.

**One non-blocking guardrail to verify during v6.0 implementation:** `paradigm_lore_record({type:'decision'})`'s rejection path must return a structured error envelope, not throw uncaught. Add a regression test asserting the shape of the response when `type === 'decision'` arrives in v6.0.
